# Release Drafter

[Release Drafter](https://github.com/release-drafter/release-drafter) is a GitHub Action that keeps a draft GitHub release up to date. The draft lists the pull requests merged since the last release, with their authors. This page is for maintainers of a project created from Scaffold. It covers when the draft updates, how it gets its version and what each setting in its configuration does.

## Workflow

The `Draft release notes` workflow, `.github/workflows/draft-release-notes.yml`, runs Release Drafter on every push to the `main` branch and on every tag push. Each run updates the draft from `.github/release-drafter.yml`. The workflow authenticates with `GITHUB_TOKEN`, the token GitHub creates for every run, so it needs no secret.

To release, publish the draft on your repository's **Releases** page. Edit it first if you need to. The Scaffold repository's [Releases](https://github.com/AlexSkrypnyk/scaffold/releases) page shows releases drafted this way.

`init.sh` keeps Release Drafter by default. To leave it out of a new project, answer no to the `init.sh` prompt **Use GitHub release drafter**, or pass `--no-release-drafter`. To remove it from an existing project, delete `.github/workflows/draft-release-notes.yml` and `.github/release-drafter.yml`.

## Version schemes

The workflow reads the `RELEASE_VERSION_SCHEME` repository variable to pick the versioning scheme of each draft:

| `RELEASE_VERSION_SCHEME` | Scheme | Next version |
|---|---|---|
| Unset, or any value other than `calver` | [Semantic Versioning (SemVer)](https://semver.org/) | The last release's version with the minor part bumped, so `2.4.3` becomes `2.5.0` |
| `calver` | [Calendar Versioning (CalVer)](https://calver.org/) | `YY.M.0` from the run date, such as `25.1.0` for January 2025 or `25.12.0` for December 2025 |

Under CalVer, the patch number is always `0`. After you publish a release, the next draft in the same month gets the same version and tag as that release.

Set the variable on the **Variables** tab of your repository's **Settings > Secrets and variables > Actions**. After you set it to `calver`, the **Set version** step of the next `Draft release notes` run logs `Using CalVer:` and the version.

## Configuration

Scaffold's [`.github/release-drafter.yml`](https://github.com/AlexSkrypnyk/scaffold/blob/main/.github/release-drafter.yml) sets the release name, the tag and the layout of the notes:

import CodeBlock from '@theme/CodeBlock';
import MyComponentSource from '!!raw-loader!../../../../.github/release-drafter.yml';

<CodeBlock language="jsx">{MyComponentSource}</CodeBlock>

Several settings use `$RESOLVED_VERSION`, the next version. Under SemVer, Release Drafter calculates it from `version-resolver`. Under CalVer, the workflow passes the CalVer version to Release Drafter, which uses it as `$RESOLVED_VERSION`.

The following table describes each setting:

| Setting | Effect | Example |
|---|---|---|
| `name-template` | Sets the release name. | A next version of `2.5.0` names the draft `2.5.0`. |
| `tag-template` | Sets the Git tag that publishing the release creates. | A next version of `2.5.0` creates the tag `2.5.0`. |
| `change-template` | Formats each merged pull request from its title (`$TITLE`), its author's username (`$AUTHOR`) and its number (`$NUMBER`). | Pull request 42, titled `Fix bug` and opened by `Alice`, appears as `- Fix bug @Alice (#42)`. |
| `change-title-escapes` | Escapes `\`, `<`, `*`, `_` and `&` in `$TITLE`, so Markdown doesn't format them. | `Fix <bug> & improvements` appears in the Markdown as `Fix \<bug> \& improvements`. |
| `version-resolver.default` | Sets the version part to bump when no label rule matches. A label rule maps pull request labels to a version part, and the file defines none, so every SemVer draft bumps the minor version. | `2.4.3` becomes `2.5.0`. |
| `template` | Sets the layout of the release notes. | See the following table. |

To stop titles from creating mentions, add `@` to the `change-title-escapes` string. Add `#` to stop issue links, and a backtick to stop code formatting. The author mention comes from `@$AUTHOR` in `change-template`, so it stays.

The following table lists the lines of `template`:

| Line | Renders as |
|---|---|
| `## What's new since $PREVIOUS_TAG` | A heading naming the last release's tag, such as `## What's new since 2.4.3` |
| `$CHANGES` | Every merged pull request, formatted by `change-template` |
| `**Full Changelog**: https://github.com/$OWNER/$REPOSITORY/compare/$PREVIOUS_TAG...$RESOLVED_VERSION` | A link that compares the last tag with the new version, such as `https://github.com/owner/repo/compare/2.4.3...2.5.0` |
| `$CONTRIBUTORS` | The usernames of the people who authored or committed changes in the release, such as `@Alice and @Bob` |

For 2 merged pull requests, `$CHANGES` renders as:

```text
- Fix bug @Alice (#42)
- Add feature @Bob (#43)
```
