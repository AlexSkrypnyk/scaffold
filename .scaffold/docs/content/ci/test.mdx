# Test

Scaffold ships a test workflow for each stack a project uses. This page is for maintainers of a project created from Scaffold. It lists what each PHP, Node.js, Shell and Actions job checks, and the repository variables that change them. The Docker and documentation workflows have their own pages: [Docker testing](../docker/testing.mdx) and [Documentation](../documentation.mdx).

## Trigger conditions

Every test workflow, including the Docker and documentation workflows, runs on the following events:

- A pull request that targets `main` or any branch that begins with `feature/`, such as a pull request from `feature/new-button` to `feature/new-layout`.
- A push to `main`, such as the merge of a pull request.
- A daily scheduled run at 04:23 UTC, which shows whether the project still builds when nobody has pushed. To leave it out, run `install.sh` with `--no-schedule` or answer no to **Use scheduled builds**. In an existing project, delete the `schedule` block from each `.github/workflows/test-*.yml` file.

You can also start the PHP, Node.js, Shell and Docker workflows by hand from the **Actions** tab.

## Windows

The PHP, Node.js and Shell workflows can also run their jobs on `windows-latest`. `install.sh` leaves Windows out of new projects by default. To add it, answer yes to **Use Windows in CI** or pass `--windows`.

Each job name ends with its runner, such as `PHP 8.4, Deps normal, windows-latest`. Linting, the coverage threshold and the coverage uploads run on `ubuntu-latest` only. On Windows, each job turns off Git's line ending conversion before the checkout, so scripts and fixtures keep LF line endings. The Node.js jobs also run the npm scripts with Git Bash, because `cmd.exe` doesn't expand the `tests/nodejs/*.test.js` glob.

To remove Windows from an existing project, delete the `windows-latest` matrix entries and the Windows-only steps from each `.github/workflows/test-*.yml` file.

## Test PHP

The `Test PHP` workflow runs 6 jobs on `ubuntu-latest`: PHP 8.3, 8.4 and 8.5, each with 2 dependency sets. `Deps normal` installs the latest versions `composer.json` allows, and `Deps lowest` installs the lowest allowed versions. Composer installs with `--no-scripts`, and on PHP 8.5 also with `--ignore-platform-reqs`. With [Windows](#windows) on, the same 6 jobs also run on `windows-latest`.

The following table lists which jobs run each check:

| Check | Jobs |
|---|---|
| `composer validate` and `composer normalize --dry-run` | All |
| Linting with `composer lint` | `PHP 8.4, Deps normal, ubuntu-latest` |
| Tests with coverage through `composer test-coverage` | All |
| Line coverage of at least the [`CI_CODE_COVERAGE_THRESHOLD`](#repository-variables) value | `PHP 8.4, Deps normal, ubuntu-latest` |

Every job uploads the `.logs` directory as an artifact. For the coverage comment and the Codecov upload, see [Code coverage](#code-coverage).

In a command app with a PHAR, a separate `Build PHAR` job runs on PHP 8.4. It builds the PHAR with `composer build` and runs the PHAR to confirm it starts.

## Test Node.js

The `Test Node.js` workflow runs 3 jobs on `ubuntu-latest`: Node.js 20, 22 and 24. Each job installs dependencies with `npm install --ignore-scripts`. With [Windows](#windows) on, the same 3 jobs also run on `windows-latest`.

The following table lists which jobs run each check:

| Check | Jobs |
|---|---|
| Linting with `npm run lint` | `Node.js 24, ubuntu-latest` |
| Tests with coverage through `npm run test-coverage` | All |
| Line coverage of at least the [`CI_CODE_COVERAGE_THRESHOLD`](#repository-variables) value | `Node.js 24, ubuntu-latest` |

Every job uploads the `.logs` directory as an artifact.

## Test shell

The `Test shell` workflow runs 1 job on each of these runners: `ubuntu-latest`, `ubuntu-24.04`, `macos-latest` and `macos-15`. Ubuntu and macOS each run their latest image and the version before it. With [Windows](#windows) on, 1 more job runs on `windows-latest` under Git Bash. On macOS, the job first installs the current Bash with Homebrew. Every job installs the BATS testing framework with `npm ci --ignore-scripts` in `tests/bats`.

The following table lists which jobs run each check:

| Check | Jobs |
|---|---|
| Linting with ShellCheck and shfmt | `Shell, ubuntu-latest` |
| BATS tests, with coverage measured by kcov | `Shell, ubuntu-latest` |
| BATS tests | Every other runner |

The `Shell, ubuntu-latest` job uploads the coverage report as an artifact.

## Test Actions

The `Test Actions` workflow runs on `ubuntu-latest` and lints and audits the workflow files in `.github/workflows`. `install.sh` leaves it out of new projects by default. To add it, answer yes to **Use GitHub Actions linting** or pass `--test-actions`.

The following table lists its checks:

| Check | Configuration |
|---|---|
| [`yamllint`](https://github.com/adrienverge/yamllint) lints the workflow YAML. | [`.github/.yamllint-for-gha.yml`](https://github.com/AlexSkrypnyk/scaffold/blob/main/.github/.yamllint-for-gha.yml) |
| [`actionlint`](https://github.com/rhysd/actionlint) lints the workflows. | None. To use a runner label missing from the `actionlint` built-in list, add a [`.github/actionlint.yaml`](https://github.com/rhysd/actionlint/blob/main/docs/config.md) file. |
| [`zizmor`](https://docs.zizmor.sh/) runs security analysis and uploads the results to the repository's **Security** tab. | `zizmor.yml` in the repository root lists the accepted findings and explains each one. |

## Repository variables

The following table lists the repository variables the test workflows read. Set them on the **Variables** tab of your repository's **Settings > Secrets and variables > Actions**.

| Variable | Value | Effect |
|---|---|---|
| `CI_LINT_IGNORE_FAILURE` | `1` | Lets the PHP, Node.js, Shell and Docker jobs pass when linting fails |
| `CI_TEST_IGNORE_FAILURE` | `1` | Lets the PHP, Node.js and Shell test steps pass when tests fail. The coverage threshold check still runs and can fail the job |
| `CI_CODE_COVERAGE_THRESHOLD` | A whole-number percentage, `80` by default | Sets the minimum line coverage for the PHP and Node.js coverage checks |
| `CI_ACTIONLINT_IGNORE_FAILURE` | `1` | Lets the Actions job pass when `yamllint` or `actionlint` fails |
| `CI_ZIZMOR_IGNORE_FAILURE` | `1` | Lets the Actions job pass when `zizmor` fails |

## Code coverage

The following table lists the job in each workflow that reports coverage:

| Workflow | Job | Coverage report |
|---|---|---|
| `Test PHP` | `PHP 8.4, Deps normal, ubuntu-latest` | `.logs/cobertura.xml` |
| `Test Node.js` | `Node.js 24, ubuntu-latest` | `.logs/cobertura-coverage.xml` |
| `Test shell` | `Shell, ubuntu-latest` | `.logs/.coverage-html` |

On a pull request, the PHP job posts the summary from `.logs/coverage.txt` as a new comment and hides the previous one. The following screenshot shows that comment on an example [pull request](https://github.com/AlexSkrypnyk/scaffold/pull/39):

![The coverage summary that the Test PHP workflow posts as a pull request comment](/img/coverage.png)

Each of these jobs sends its report to [Codecov](https://about.codecov.io/) with the [`codecov/codecov-action`](https://github.com/codecov/codecov-action) action. The PHP job also sends its test results. The uploads run only when the repository has a `CODECOV_TOKEN` secret, and a failed upload fails the job.

To set up the uploads:

1. Add your repository to Codecov and copy its token, as the [Codecov quick start](https://docs.codecov.com/docs/quick-start#section-add-repository) explains.
2. Add the token as the `CODECOV_TOKEN` repository secret.
