# CLI command

In CLI command mode, your project is a console app built on the [Symfony Console component](https://symfony.com/doc/current/components/console.html). Use it for a tool with several commands or shared logic. For a tool that does 1 task with no dependencies, see [CLI script](./php-script.mdx).

This page is for developers building a command-line tool from Scaffold. It covers how the app is laid out, how to add and test a command and how to ship the tool.

`init.sh` selects this mode by default. It replaces `php-command` with your project name, or with the value of `--php-command-name`, in filenames and file contents. This page uses the template name.

## Application structure

The app has 2 parts:

- **The launcher**, [`bin/php-command`](https://github.com/AlexSkrypnyk/scaffold/blob/main/bin/php-command). It loads the Composer autoloader, creates a Symfony Console `Application`, registers each command and runs the app.
- **The command classes**, in [`src/Command/`](https://github.com/AlexSkrypnyk/scaffold/tree/main/src/Command). Each class extends `Symfony\Component\Console\Command\Command` and holds the logic of 1 command.

Symfony Console parses arguments and options, prints help and styles the output.

The launcher makes `JokeCommand` the default with `setDefaultCommand()`, so `./bin/php-command` with no command name runs `joke`.

## Example commands

The following table lists the 2 example commands:

| Class | Command name | What it does |
|---|---|---|
| `SayHelloCommand` | `say-hello` | Prints `Hello, Symfony console!` and returns `Command::SUCCESS`. Sets a description and a help text. |
| `JokeCommand` | `joke` | Fetches a random joke from `https://official-joke-api.appspot.com/jokes/TOPIC/random` and prints its setup and punchline. The optional `--topic` option sets `TOPIC` and defaults to `general`. If the request fails or the joke lacks a setup or a punchline, prints `Unable to retrieve a joke.` and returns `Command::FAILURE`. |

After `composer install`, run the `say-hello` command from the project root:

```bash
./bin/php-command say-hello
```

The command prints `Hello, Symfony console!`.

## Add a command

Start from `SayHelloCommand` for a command with no input, or from `JokeCommand` for one with options.

To add a command of your own:

1. Copy `SayHelloCommand.php` or `JokeCommand.php` in `src/Command/` to a new file named after your new class.
2. In the new file, rename the class to the filename without `.php`.
3. In `configure()`, set the name, description and help text of the command and add its arguments and options.
4. In `execute()`, replace the example code with your logic. Return `Command::SUCCESS` or `Command::FAILURE`.
5. In `bin/php-command`, add a `use` line and an `$application->add()` call for your class, the same way the launcher registers `SayHelloCommand`.
6. Add a test for the command in `tests/phpunit/Functional/`. See [Test a command](#test-a-command).
7. Run the command:

   ```bash
   ./bin/php-command COMMAND_NAME
   ```

   Replace `COMMAND_NAME` with the name you set in `configure()`. Confirm that the output matches what `execute()` writes.

## Test a command

The command tests live in [`tests/phpunit/Functional/`](https://github.com/AlexSkrypnyk/scaffold/tree/main/tests/phpunit/Functional). They use `ApplicationTrait` from [`alexskrypnyk/phpunit-helpers`](https://github.com/AlexSkrypnyk/phpunit-helpers), which wraps Symfony's `ApplicationTester`. The trait's main methods are:

- `applicationInitFromCommand()`, which builds an app around 1 command
- `applicationRun()`, which runs the app and returns its output

[`SayHelloCommandTest.php`](https://github.com/AlexSkrypnyk/scaffold/blob/main/tests/phpunit/Functional/SayHelloCommandTest.php) checks the greeting. [`JokeCommandTest.php`](https://github.com/AlexSkrypnyk/scaffold/blob/main/tests/phpunit/Functional/JokeCommandTest.php) mocks `getContent()`, so `JokeCommand` gets fixture responses in place of calls to the API.

Both tests belong to the `command` group. To run only that group:

```bash
composer test -- --group=command
```

For the PHPUnit configuration and coverage reports, see [Testing](./testing.mdx).

## Distribution

A CLI app ships as a PHAR file, as a Composer package or as both. The template supports all 3 from 1 layout:

- The app code lives in `src/`.
- A thin launcher, `bin/php-command`, loads the Composer autoloader and runs the app.
- `composer.json` lists the launcher under `bin`.

Composer, Box, PHP-Scoper and Rector ship their own executables with the same `bin/<name>` launcher layout.

### As a PHAR

A PHAR is a single executable file that bundles the app and its dependencies. Users need only PHP to run it.

`composer build` compiles the PHAR into `dist/php-command.phar`. Git ignores `dist`, so the PHAR stays out of your commits. When you push a tag, the `Release PHP` GitHub Actions workflow builds the PHAR, creates a release for the tag and attaches the PHAR to it. For the Box configuration, see [PHP packaging](/ci/php-packaging).

The PHAR build is on by default. With `--no-phar`, or "n" to the `Build PHAR` prompt, `init.sh` removes the Box configuration, the `build` script, the `Build PHAR` job of the `Test PHP` workflow and the `Release PHP` workflow.

### As a Composer package

Publish the project to Packagist.org, the Composer package registry. Composer links every `bin` entry into the `vendor/bin` directory of the project that requires the package. That project runs `vendor/bin/php-command`.

The launcher looks for the requiring project's autoloader before its own, so it runs both as a dependency and from its own checkout.

### As both

Use the single launcher for both. Composer links `bin/php-command`, and Box compiles the same file into the PHAR. A change to the launcher reaches Composer installs and the next PHAR build.

### PHAR through Composer

Some tools, such as PHPStan, commit the built PHAR to their Composer package and point a small `bin/` launcher at it. Composer users of those tools get the compiled build. The template ships the source through Composer. Composer downloads the package from your Git repository, where `dist` is ignored, so the PHAR stays out of the package.
